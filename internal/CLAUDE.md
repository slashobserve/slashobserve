# Backend conventions

Rules for `internal/` and `cmd/`.
The rules for `pkg/` are in the root `CLAUDE.md`.

## Packages

This lists only the packages whose purpose the name does not make obvious.

- `config`: the only reader of `SLASHOBSERVE_*` environment variables (`config.Load`).
- `actor`: who made a write and how it is shown: `Actor` (principal kind, id, name, origin and client, and the agent request id), its column mapping, and `Label` and `ClientName`, the only place an actor or an MCP client name becomes display text for the web, the CLI and MCP.
- `logattrs`: turns an error into log attributes that are safe to write.
- `llm/pricing`: the one model price table (embedded `prices.yaml`, replaced whole by `SLASHOBSERVE_LLM_PRICES_FILE`), read by run costs and the run cost limit; a model without a complete price is never priced as zero.
- `logvolume`: level words to kinds and the volume histogram the logs volume endpoint returns.
- `logpatterns`: the pure token masking and line clustering the log patterns endpoint runs when a datasource has no pattern index.
- `db`: pgx pool, goose `migrations/`, sqlc `queries/`, generated `dbsqlc/`.
  `dbtest` gives each test its own migrated database from one Postgres testcontainer per test binary (`dbtest.Main` in `TestMain`, `dbtest.New(t)`; skipped under `-short`).
- `fleet`: each server's heartbeat into `server_instances` (10 s, stale after 30 s, times from Postgres only) and `Share(total)`, the one rule for dividing a fleet-wide total among live servers.
- `tctest`: retry for testcontainers starts that fail on testcontainers-go reaper (ryuk) start errors; every container start in tests goes through it.
- `folders`: folders, permissions and the one place that decides who sees and changes a dashboard.
- `forbidden`: the `forbidden_role` code and its 403 texts, a leaf package so the CLI can compare against them without the server.
- `egress`: the only fetcher of user-supplied URLs; `egress/allowlist/` holds the outbound domain table, routes and the `SLASHOBSERVE_OUTBOUND_DOMAINS` lock; `Client.CallTripper` is the round tripper for a caller that speaks its own protocol, such as the MCP client, and keeps the allowlist, address and redirect rules on any port; `Client.PrivateCallTripper` keeps the allowlist and domain-name rules but allows `http` and private addresses, and only an MCP source whose provisioning entry sets `allowPrivate` (never the API, CLI or web) reaches it.
- `sealed`: encrypts stored secrets with `SLASHOBSERVE_SECRET_KEY`, one HKDF purpose label per kind of secret and the owning row's id as additional data; the only place a stored secret is sealed or opened.
- `queryproxy`: panel query runner shared by save validation and the proxy.
  `queryproxy.Slots` is the one gate on datasource calls: a datasource's `maxConcurrentQueries` (default 32, fleet-wide) divided by `fleet.Membership.Share`, then 32 per process across all datasources; both runners share one `Slots`, and every `AcquireUpstream` names its datasource.
  A limit is divided among servers with `Share` only when it caps a total over every caller of a resource all servers share that has no backpressure (datasource calls); a per-caller limit or a limit on the process's own capacity stays per process.
  `queryproxy/proxyhttp` holds its HTTP handlers, a subpackage because it reads versions through `dashboards`, which imports `queryproxy`.
- `agent`: no code of its own; `agent/tools` is the only place agent tools are defined, `agent/guard` holds the run guards, `agent/brief` the seed and digest text, `agent/triage` the preflight sweep of an investigation, `agent/route` the task type of an investigate run and `agent/prompts` the embedded prompts.
  `route.Classify` is pure: fixed rules over the question's words, the run's subject and the configured datasource types, no model call; `runsession` calls it once in `Service.initial` for an investigate run, stores `State.Task` with the session and records one step that names the type and never the question.
  `Scope` carries it as `tools.Run.Task`, and `Tool.OfferedInRun` is `OfferedInMode` (the mode rules) and `Tool.InTask` (`agent/tools/tasktools.go`: `taskBasics`, `taskTools` and the subject reads), so a type only narrows; the run transports are built from `OfferedInMode` and `listableRunTools` drops what `InTask` leaves out per request, so the built-in agent and a connected agent list the same tools, and `Registry.call` answers a mode-offered tool outside the type with `unknown_tool` and the type's tool names.
  `prompts.InvestigateFor(Variant, types)` is the one assembly of an investigate system text: the core `investigate.md`, the playbook of `Variant.Task` from `playbook/` (every playbook behind `playbook/full.md` for no type), the facts section in place of `enforcedRules` with grounding on, `ledger.md` with the loop, then the scope and `GuideFor(types)`; `brief.Render` passes `Task.Route` from `State.Task`, and `playbook_test.go` keeps every type and variant under the size of the text before task types, so a new rule goes into the one playbook it belongs to or is enforced in code instead.
  `list_more_tools` (agent-only, offered only in a sorted run) sets `Result.AllTools`, which `runsession` stores as `State.AllTools` for the rest of the run, and observe-agent lists its tools again after a successful call; `TestEachTaskTypeOffersItsOwnTools` pins the lists.
  A tool file registers its entries with `registerEntries` in its own `init` and keeps its `name`, `desc`, `prop` and `schema` constants, its role assertion and its text under the 2000-byte agent cap (`wording_test.go`) in that file; `schemas.go` holds only the shared `prop*` constants; `TestToolsLeftOutOfRuns` pins the tools of `leftOutOfRuns` (`runtools.go`, each with its reason), `TestToolsOfferedInInvestigationsAndChatQuestionsOnly` pins the three MCP source tools of `contextReads` (same file, `Tool.OnlyIn` and `Tool.AlsoInChats`, offered in an investigate run and in a chat question only), `TestRunsOfferEveryToolNotLeftOut` fails on a tool that is neither offered in a run nor left out, and `TestAgentDocsStateTheToolCountsOfTheRegistry` (`internal/agent/tools/docs_test.go`) checks the counts in `docs/concepts/agent.md`, so a new tool left out of runs updates all three.
  `docs/use/mcp.md` has one row per MCP tool with its lowest role, and `docs_test.go` fails when a tool has no row or the wrong role.
- `agent/prompts/skill`: the `/observe` skill file and its body, a leaf package so the CLI can embed it without the Spec; the MCP prompt `observe` serves its body.
- `drafthttp`: `POST /datasources/{uid}/draft-query`, the HTTP face of `tools.Registry.DraftQuery`, which the `draft_query` MCP tool also calls; drafts are synchronous and stored nowhere, limited in process (3 per caller in flight, 10 per process) and by `draftbudget` (60 per caller per clock hour, counted in `draft_query_spend`).
- `tailhttp`: `GET /datasources/{uid}/tail`, the SSE live tail; one poller per stream, 5 per person, no query slot.
- `tracecompare`: the pure ranking of attribute values that set selected traces apart from a baseline, shared by `POST /datasources/{uid}/trace-compare` and the `compare_traces` tool; the adapters read the pairs through `datasource.TraceAttributeSource` (Tempo at 4 traces at a time, ClickHouse in one query).
- `activity`: the persisted activity log: `Append` is the only writer, `Store` reads it per audience (`List`, and `Start` and `Next` for followers), `Handler` serves `GET /activity`, and `events/stream` serves `GET /activity/stream`; the inbox is a reader of the same log, not a second store: `Store.Inbox` and `MarkRead` serve `GET /inbox` and `POST /inbox/read` from the `inbox_reason` SQL function (the one place that decides why an event needs a person), with the horizon and the scan in one statement as every activity read, and the only new state is `inbox_cursors`, one `(xid, seq)` read position per person that only moves forward.
- `lifecycle`: the generic `Machine[S, A]` (states, moves, and the `Who` that may make each) and `Derived` for states computed on read; a move the machine refuses answers 409 `invalid_transition` with `allowed_actions` (`AbortRefusal`), and `docs/reference/states.md` is rendered from the machines by `internal/surface` (`TestStatesReferenceIsCurrent`).
- `proposals`: a change waiting for an Editor to merge: `Service` is the one writer of `proposals` and `proposal_revisions` through `Propose`, `Merge` and `Discard`, moves them only through `ProposalMachine`, and appends the `proposal.*` activity events; `Merge` saves through `dashboards.Service.Save`, so a proposal never writes a version itself.
- `observations`: the observation, its blocks, snapshots and RCA revisions: `Service` is the one writer, moves them only through the observation and block machines, and appends the `observation.*` events; an RCA revision's `state` is computed on read by `rcaState` from its live public links and the newest revision, `RCAMachine` (`rca_machine.go`) decides its `allowed_actions` and who may withdraw it, and a refused publish or withdraw is an `RCARefusal` that keeps its code and adds `state` and `allowed_actions`; a person who can only comment adds a requested block, which an editor keeps or discards.
  A chat with no dashboard and exactly one observation whose `run_id` is one of its turns shares its title with it: the `ChatObservations` query is the one link, `Service.Update` renames the chat in the observation's transaction only for the chat's requester, and `Service.RenameFromChat`, reached through `ObserveOptions.ShareTitle` after `UpdateListFields`, renames the observation only when the caller may update it, so `revisions` still never imports `observations`; either answers `renamed` or `kept`, and nothing for an observation the caller cannot see.
- `grantmode`: the `direct` or `propose` mode of a connected agent's grant as a value in the request context; `internal/server/mcp` sets it from the credential's grant, and the save paths read it with `grantmode.From`.
- `presence`: `Of` turns an agent's last claim and held run into `working`, `listening` (a claim in the last 40 seconds) or `offline`, the one rule behind the Agents page, `GET /agents` and the `presence` states.
- `agentsview`: `GET /agents`, a read-only overview of the Observe Agent, the caller's live connected agents and the run-taking service accounts; it reads `agent_requests`, `oauth_grants`, `agent_workers` and `activity` through `Queries` and writes nothing, takes presence from `presence.Of`, and a run's `run_usage->>'cost_usd'` is the only cost source, so a finished run without one is counted in `unpriced_runs` and left out of the `cost_usd` sum, which is null only when no run has a cost.
- `search`: one ranked full-text query over dashboards (latest version), observations (title, summary and live text blocks, which hold a finding's text), annotations, comments and saved searches, read from the expression indexes of migrations 33 and 38 with visibility joined in the same statement as titles and snippets (dashboard folder, observation folder, General for global annotations, a comment through its thread's target, saved-search folder); a finding is found only as its observation and `finding` is not a kind; no service writes anything for search, so every write, cascade and move is reflected at once.
- `webhooks`: Admin-configured outgoing webhooks: `Service` is the one writer of `webhooks` and `webhook_deliveries`, and `Worker` delivers activity events to each webhook in log order from a cursor `(cursor_xid, cursor_seq)` on its row, reading through `activity.Store.Next` as the webhook's owner, so nothing is written in a change's transaction and `activity.Append` knows nothing of webhooks.
- `inboundmcp`: Admin-registered MCP servers and their tools, called MCP sources in the product (the servers this server reads from as a client, not `internal/server/mcp`, the `/mcp` endpoint outside agents connect to): `Service` is the one writer of `mcp_sources` and `mcp_source_tools`, the server is the MCP client (`MCPConnector`, through `egress.Client.CallTripper`; `open` speaks streamable HTTP and falls back to the legacy SSE transport only when the source answers the initialize POST with a 4xx, through the same tripper), secrets are sealed with `sealed.Key`, and `reconcile` (`tool.go`, pure) is the one place that decides a tool's state after discovery: nothing new is approved, a tool whose hash changed becomes `changed` and stops being served, and a missing one becomes `gone`; a tool is moved only through `ToolMachine`.
  `refusalOf` refuses only a tool marked `destructiveHint: true` or with a description or schema over the limits; the read-only mark (`read_only`, migration 98) is stored with the pinned and the seen definition and is part of the hash only when it is false, so read-only tools pinned before keep their hashes and a tool that stops being marked read-only becomes `changed`; `ApproveReadOnly` approves only offered tools marked read-only, so any other tool is approved by name, and `approveListedOf` treats a tool that was `refused` before the discovery as never decided, so a file's `approve` list approves a tool refused as unmarked before the upgrade.
- `grafanaconn`: Grafana connections and imports: an import is a `grafana_syncs` row moved only by `SyncMachine` (`internal/grafanaconn/machine.go`), held by a 60 second lease renewed every 10 seconds, with one `grafana_sync_items` row per dashboard written under that lease; a stopping server releases the lease and any server's resume pass claims it, a second lease expiry fails it, and each connection keeps 20 imports.
- `findings`: an adapter over observations: it stores investigate results and the answers of new-dashboard and revision requests that only ask a question; `revisions` reads them only through sqlc and the `ObserveOptions.Finding` func, and never imports `findings`.
  A save in a run that has an observation (every investigate run opens one at enqueue) writes the conclusion blocks through `findings.Observations` (`observations.Service.WriteConclusion`) in the finding's own transaction, so a failure leaves neither.
  A save in a run without one is a chat-only answer: `findings.observation_id` is NULL (migration 65, with a check that a row without an observation names its run and a trigger that deletes it with its run), no observation and no `finding.created` activity exist, and the answer stays on the run.
  `findings.Service.SaveAsObservation` is the only way such an answer becomes an observation: it locks the row, calls the same `WriteConclusion` with the stored text and evidence, and sets `observation_id`; it is idempotent and only the requester may call it (`POST /observe/{id}/observation`, `save_run_answer`, `observe save-answer`, through `ObserveOptions.SaveAnswer` so `revisions` still never imports `findings`).
  A saved finding takes placement and access from its observation (`observations.Service.Placement`), so `findings.folder_id` is never written, nothing moves a finding (its observation moves through `observations.Service.Move`) and a saved finding cannot be unfiled.
  An unsaved answer is read by its requester and Admins only, and on a dashboard only while the reader can still view that dashboard (the `ViewBuild` rule, so an Admin never reads one on a dashboard in someone's personal folder); it is never listed, cannot be pinned, and can be made a dashboard by its requester.
  A saved finding's address is `links.Observation`, an unsaved one's is the run's chat (`links.Chat`), and `threads` and `search` never import `findings`.
- `savedsearches`: saved logs, trace and metrics searches: `Service` is the one writer of `saved_searches` and appends the `saved_search.*` activity events; it takes folder access from `folders`, decides which datasource types fit each kind through pure functions in `validate.go`, and never runs a query.
- `threads`: comment threads on a dashboard, an annotation, an observation or a proposal: `Service` is the one writer of `threads`, `thread_messages` and `thread_mentions`, takes access from `dashboards`, `annotations`, `observations` and `proposals` through their `Access` methods, and appends the `thread.*` activity events; message bodies never enter an event's `data`.
  A `finding:<id>` target is refused as an invalid target; no thread has a `finding_id`.
  `Threads` serves `/threads` and `/messages` over `Service` for every target; a thread id route also takes any message id of the thread, and only the legacy adapter can queue a revision.
  A mention is `@[Name](user|grant|service_account:<id>)` or the bare `@observe`; a grant must be the author's live connected agent and a service account must take runs (`recordMentions`, 422 `invalid_mention`), and a key author may not mention a grant.
  `Asks` is the one place a message asks an agent: `recipientOf` (`recipient.go`, checked against `spec/examples/threads/recipient-cases.json`) decides from the body, `to` and the thread's agent (`threads.agent_kind`, `agent_id`, `agent_off`) who is asked and how the thread's agent changes; it counts agent mentions first (`too_many_agents`), runs `revisions.CheckRun` before the transaction, re-decides on the locked thread inside it, writes the thread's agent with a `thread.agent_set` audit event, and enqueues in the message's own transaction through `MessageHook` (`EnqueueAssigned`, `EnqueueAssignedInvestigate` with `Ask`, which skips the investigation caps), with `trigger = 'mention'`, `thread_message_id`, the thread's anchor and block (the message's own `block_id` instead when it names one, which also drops an anchor that sat on another block), and the last 20 earlier messages (8000 runes) as `thread_context`; only cap refusals (`too_many_runs`) leave the message committed, any other enqueue error rolls it back.
  A thread agent that is no longer mentionable is cleared and answers `agent_unavailable`, and someone else's live grant stays and answers `agent_not_yours`; HTTP defaults `to` to the recipient rule and MCP and the CLI to `everyone`.
  `client_id` is unique per author on `thread_messages`: a resend is `ON CONFLICT DO NOTHING`, rolls back and re-reads the stored message with `replayed`, and starts nothing.
  An observation has one page thread (`threads_observation_page_idx`, no anchor and no block) and any number of anchored ones; `Asks.Open` turns a lost race for the page thread into a reply.
  The assignee is `builtin` for `@observe`, which needs the model provider, and a grant or service account for its token, which needs none.
  The legacy dashboard comment routes and the agent comment tools are the `Comments` adapter over `Service`, and `Runs` is the revision queue's view of threads (`ForRun`, `RunEnded`), so `internal/revisions` never imports `threads`.
  Every thread write locks the owning dashboard row `FOR KEY SHARE`, then the annotation, observation or proposal row the same way, before it writes or appends, so a delete (which holds `FOR UPDATE` and cascades into threads) never deadlocks with a thread write and a late writer finds the target gone.
  `Runs.RunEnded` is the one answer to a run that reached a terminal state: a run with `thread_message_id` (a mention run) posts one server-written status reply in that thread and never resolves it, and any other run keeps resolving its comment thread when it saved a version.
  The reply's author is `revisions.AssigneeActor`, the one decision derived from the run's assignee: the built-in agent is `RunActor` (the requester with `run_id`, shown as "Observe Agent for <name>"), a connected agent is the requester with origin `mcp` and the grant's client name ("<name> (via <client>)") and a service account is its own actor with origin `mcp`; `thread_messages.run_id` holds the run id for every reply and `run_assigned_kind` the assignee kind, and `messageOf` exposes `run_id` on the author only for the built-in agent, because the web reads a run id as the built-in agent's mark; `thread_messages.run_failed` marks the reply of a run that ended failed, the one the inbox leaves out while the run's `run_failed` item stands; `InsertRunReply` is a no-op when the run already replied; it appends `thread.replied` like a person's reply and does not reopen a resolved thread.
  Its text is composed in `internal/threads/runreply.go` from the run row, the proposal title and fixed strings, never from model text, so a connected agent's `finish_run` message is not repeated; a run that saved an answer replies `Answered.`.
  `Service.List` carries each run reply's answer (`Message.Answer`) through `ReadAnswersWith`, only when the query asks `WithAnswers` (the thread routes and `list_comments`, not the legacy dashboard comments list): one query keeps the page's runs that saved a finding, each of those passes `revisions.Service.ShowsRunAnswer` (the decision of `ReadObserve` and the run view's `findingShown`, without recording `run.view`, because a list is not recorded) and then reads its finding through `findings.Service.ForRequest`, which `cmd/slashobserve-server/main.go` adapts, so a reader gets exactly the answer the run read gives them and no second access rule exists; the web, `list_comments` and `observe comments list` read it there, never through a per-reply `GET /observe/{id}`.
  `RunEnded` takes the target lock `SKIP LOCKED`, because the finishing run already holds its own agent request row: a dashboard or observation being deleted skips the reply instead of waiting for it.
  `dashboard_comments` is frozen after migration 00028: nothing reads or writes it, and the migration's Down rebuilds it from threads.
- `mcpauth`: the OAuth 2.1 authorization server for MCP clients: metadata, dynamic registration, authorize, token, revoke, the consent and connected-agent API, and `Authenticate`, the only reader of OAuth access tokens; `cmd/slashobserve-server/main.go` composes it with service-account keys for `/mcp`, so `auth` never imports it.
- `stars`: each person's starred dashboards, stored on the server so they follow the person across browsers; keys get 403 `user_session_required`, and recently viewed dashboards stay in the browser.
- `public`: public links to a dashboard or to one revision of an RCA, their tokens, the public Spec without query text, the frozen and free variable rule (`EffectiveSelections`) and the stored RCA view with its snapshot frames, which never touch the live observation; `proxyhttp` imports it, never the reverse.
- `health`: the `dashboard_health` job, registered hourly in `cmd/slashobserve-server/main.go`, the `/health` routes and dashboard opens (`dashboard_views`, written by `POST /dashboards/{id}/views` for people only).
  `Service` holds the job, the list and views and is built before the tool registry; `Repairs` takes the revisions service.
  A run stops after 8 minutes, under the scheduler's 10 minute lease, checks 2 dashboards at once with `CheckSpec` over the last 7 days and no user.
  `DashboardsDueForHealth` is the one due rule: a dashboard is due when never checked, or when checked before this run started and either checked over 23 hours ago, stored with a `query_failed` or `variable_failed` problem, or checked at a version older than its latest.
  So healthy dashboards are checked about once a day, failures and unchecked new versions on the next hourly run, and none twice in one run.
  `duplicate_title` and `unopened` are computed on read, never stored, and a repair's prompt starts with `repairprompt.Prefix`, which the per-requester cap matches.
- `specfiles`: the dashboard file layout shared by the provisioner and the CLI; a folder directory name escapes only `%` and `/` (`DirName`, `FolderTitle`), so any title round-trips.
- `livetext`: the text a run is writing right now, shown while it runs: `Store.Append` sends a cleaned chunk on the Postgres channel `slashobserve_run_text` and every server's `Store.Run` listener keeps the newest 2000 runes per run (1024 runs, 10 minutes idle) in memory, so a reader on any replica sees it; nothing is stored in a table, a newer attempt replaces an older one, and `Text` answers only for the attempt it is asked about.
- `observeagent`: the supervisor of the built-in agent's child process (`observe-agent`, from `observe-agent/`): `FindBinary` looks it up on `PATH`, `Supervisor.Run` starts it with a fresh `sob_` token in its environment (`OBSERVE_AGENT_*`, plus `PATH`, `HOME` and `TZ` only), restarts it with a backoff of 1 to 30 seconds, stops it with SIGTERM and a 10 second grace, and releases its running runs when it exits; `Authenticate` is the one check of that token, and `relay` turns the child's stdout and stderr into server log lines with `component=observe-agent`.
  The sidecar is the only runtime, so a server built from source needs `make agent` whenever a model provider is configured, because start-up fails when `FindBinary` finds no `observe-agent`.
- `taste`: the layout and field rules used by the reference dashboards' test.
- `surface`: tests only; the `/observe` guide checks and the parity test that every API operation names its MCP tools and CLI commands or carries a reason.

## Secrets and configuration

- Never log secret values, the database URL and the OIDC client secret included.
  The LLM API key is never logged or echoed in an error.
- The datasources file never holds a secret.
  Passwords and tokens are referenced by `*Env` names that start with `SLASHOBSERVE_` or by `*File` paths.
- `SLASHOBSERVE_SERVICE_ACCOUNTS_FILE` is the only way to create a credential with no person in the loop: each account's key is read from its `keyFile`, never inline, and stored only as SHA-256.
  `auth.EnsureProvisioned` runs at boot before the server listens, marks the accounts `provisioned`, never adopts an account it did not create, and replaces the `From file` key when the file's key changes; `planProvision` is the one decision, and the API answers 409 `provisioned` to role changes and key revocation on those accounts.
- `SLASHOBSERVE_OIDC_ISSUER_URL` is used exactly as given because issuer comparison is exact.
  The issuer is the browser-facing URL, and `SLASHOBSERVE_OIDC_INTERNAL_URL` only rewrites the host of the server's back-channel.
- The CLI sends its saved key only to the server it was saved for.

## HTTP, MCP and auth

- The strict `Content-Security-Policy` (`contentSecurityPolicy` in `internal/server/server.go`) allows images only from self, `data:` and `blob:`.
  Remote images, tiles and GeoJSON must load through `/api/v1/assets/image` and `/api/v1/assets/geojson`.
- `server.New` wraps the engine in `compressReads` (`internal/server/compress.go`): gzip only for GET and HEAD responses of 1024 bytes or more and never for `text/event-stream`, because a response to another method can echo a secret it created next to user text, the shape a BREACH attack needs.
  Files under `assets/` have a build-time `.br` twin (`web/scripts/precompress.mjs`, run by `bun run build`) that `serveFile` sends with `Content-Encoding: br` when the request accepts it, so the gzip wrapper leaves it alone; the twin is never served by its own name.
- `/mcp` is mounted through `server.Options.Mounts` outside `/api/v1`, so the API contract check does not cover it.
  It accepts `Authorization: Bearer` service-account keys and OAuth access tokens (a session cookie is ignored); OAuth tokens are accepted nowhere else, and for them the registered client name is the origin client and `clientInfo` is ignored.
  It refuses an `Origin` other than `SLASHOBSERVE_PUBLIC_URL`.
  `/mcp` tries the built-in agent's `sob_` per-child token first, then keys, run tokens and OAuth; a `sob_` token is accepted only from a loopback peer and serves only the four claim tools (`claim_run`, `report_run`, `finish_run`, `get_run_brief`) through `Registry.CallClaim`, which skips the role check for tools marked `Claim` and for no other; a run token is valid only while its attempt holds the lease and the run is `running`; `claim_run` long polls skip the global MCP slot because `internal/claims` caps them.
- `claims`: the claim, report and offer side of agent runs; its `BuiltIn()` claimer is the server's own sidecar, accepted by `eligible` only with this server's instance id, and the claim answer carries `model` (provider key included) only in an offer to that claimer, so no log line, error or other claimer's offer may carry a `ModelSettings`; `ReleaseHeld` requeues the built-in claimer's running runs when its child exits.
  `claims.CleanText` is the one cleaner of agent-supplied text.
- `runsession`: every call of a run token session and the `report_run`, `finish_run` and `get_run_brief` of a claimer go through it; it holds the guards, the pending build, usage and the single `Finish`, and keeps its state in `run_sessions` so a restart or another replica resumes it; rows of runs that ended outside the session are removed only by the cascade delete.
  `with` takes a per-run in-process lock (run id and attempt, `runLocks`, keyed by the parsed run id) before an `inFlight` slot, so a busy run's queued calls wait without holding a slot or a pool connection and cannot starve other runs, step writes or the lease renewal; the `FOR UPDATE` row lock stays the guard across replicas.
  `with` releases the lock and the slot before it records steps.
  A `report_run` runs `NoteUsage` under its own 4 s bound (`usageNoteTimeout`, under the agent's 10 s report timeout); when only that bound expires, it still answers the renewed lease with the live text and build progress, and the next usage report checks the cost limit again.
  `revisions.Request.WriteOrigin` is the one decision of the origin a run's writes record: the run's own origin for the built-in agent and `mcp` with the session's client for a connected agent; the MCP run handler and `runsession` both read it.
- `Tool.MCPOnly` is set in `New` from `leftOutOfRuns`, the one list of tools no run offers, and `Tool.OfferedIn` leaves them out of every run: reads are offered in every mode, writes and `Answers` tools in every mode but suggest, and investigate never gets the Spec writers; `Tool.OnlyIn` is set to investigate and `Tool.AlsoInChats` to true in `New` from `contextReads`, and `Tool.OfferedInRun` offers `list_mcp_sources`, `find_mcp_tools` and `call_mcp_tool` in investigate runs and in a chat question (`Run.Chat`: a chat run that is neither a thread ask nor an investigation, so a home question that starts as a new-dashboard run too); the MCP run transports are keyed by mode, investigation and chat.
  Every offered write names its target in `writeTargets`, and `writeScopeViolation` refuses with `out_of_scope` a write outside the run's subject, the objects it created, the build it committed and runs of its own chat, and a write whose target id is empty; `personStateWrites` (pins, home dashboard, inbox, run list, `request_comment_access`) are offered only in a chat run, and a private ask writes nothing else.
  A run that read Admin-only data creates, renames or moves nothing into a folder others read: `placement.RunWrite` (observations, blocks, annotations, saved searches, dashboard and observation moves) and the folder writes in `folders` read the run from the actor or, for a connected agent whose actor carries none, from `actor.RunIn`, and answer `ErrRestrictedAnswer`.
  A comment write called inside an agent run is rejected with `invalid_request`, because the server answers and resolves threads after a run; the comment reads are offered; comment tools ask an agent only with `to: agent`, through `threads.Asks`, so an ask in an observation thread needs Comment on the observation like any ask there, and `investigation_person_only` remains only on `retry_run` for an investigation that writes into an observation.
- `show_panel` is the one tool whose result differs by client: `Result.Content` is the text summary and `Result.App` (carried as `runsession.Answer.App`) is the chart payload, which `invoke` sends as `structuredContent` only when the request came from a client that announced `io.modelcontextprotocol/ui` with `text/html;profile=mcp-app`, so every other client sees an ordinary tool.
  The server is stateless, so the announcement is read from the `initialize` body and kept in the `Mcp-Session-Id` label (`.ui` suffix, issued for OAuth clients too), or read from the per-request capabilities of the 2026-07-28 protocol; `withPanelUI` adds `_meta.ui.resourceUri` to the tool for such a client only.
  The chart is `web/mcp-panel.html` built by `bun run build` into `internal/server/mcp/panelapp/panel.html` (gitignored, embedded, passed to `mcp.Options.PanelApp` by `main.go`; the Dockerfile copies it from the web stage); without it the resource and the metadata are absent.
- `observe skill install` writes the skill embedded in the CLI binary and never one fetched from a server, because a skill instructs the person's own agents and the CLI talks to any `--server` it is given.
- A tool's `MinRole` is the lowest role the web app needs for the same work: Viewer for every tool except `save_finding`, which needs Editor like Investigate (`revisions.runAllowed`).
  The services' folder checks decide the rest.
  `MinRole` is checked when the tool is called, inside agent runs too except for `Answers` tools, because a run's requester is reloaded with its role; the run transports in `internal/server/mcp` hide tools above the requester's role from the listing.
  `TestToolRoles` enforces the rule.
  The observation tools and `publish_rca` are therefore Viewer tools, and the observation's folder decides what a call may do.
  An agent or MCP block write goes through the same evidence checks as a finding's panels (`checkPanel`), and a snapshot or an RCA never carries query text (`withoutQueries`).
- Every `/api/v1` route except `/api/v1/auth/*` and `/api/v1/public/*` is registered through `auth.Routes` with its lowest role (`auth.RequireRole`).
  Feature packages register through `Register(api auth.Routes)`; in `queryproxy/proxyhttp` each handler file registers its routes with `registerRoutes` in its own `init`, and `Register` only replays them.
  They never see a raw gin group, except a `server.PublicRegistrar`, whose `RegisterPublic` gets the `/api/v1/public` group: no session, `Cache-Control: no-store`, and the token in the path as the only credential.
  Only `public.Handler` (the dashboard view, the RCA view and the RCA snapshot frames) and `proxyhttp.PublicData` (panel data and variable values) register there.
  Handlers never check roles.
  `auth.RequireUser` is a separate principal-kind check after the role, so a key cannot manage keys whatever its role.
- The OIDC `groups` scope is requested only when discovery lists it in `scopes_supported`.
- Sessions, keys, public link tokens and OAuth codes, access and refresh tokens are opaque random tokens made by `opaquetoken.New` and stored only as SHA-256.
  Request and panic logs pass the path through `loggedPath`, which replaces the token of `/api/v1/public/<token>`, `/p/<token>` and `/rca/<token>` with `:token`.
- Creating, listing and revoking a public link needs Manage on the dashboard's folder; the routes declare `RequireDashboard(NeedView)` and `public.Service` decides, so a dashboard in a personal folder answers 409 `personal_folder` and one whose latest version reads `${__user.*}` answers 422 `user_scoped`.
  Cookie-authenticated mutations pass `http.CrossOriginProtection`.
- Origin, an actor and its label are display only and never an access decision; access always reads `auth.Principal`.

## Folders and access

- `folders.LevelFor` is the one rule for what a caller may do with a dashboard, shared by web, API, MCP, CLI and agent runs.
  Stored rows are never rewritten when a role changes.
- Every dashboard lives in exactly one folder.
  `dashboards.folder_id` defaults to General through `general_folder_id()`, so raw inserts land there.
- A shared folder with no permission rows is open, and each person gets the level of their role.
  A folder with rows is restricted and invisible to anyone with no row (by user or by `groups` name) who did not create it.
  A hidden folder hides its dashboards everywhere.
- A grant lifts a Viewer or Commenter and never lowers anyone: the level is the higher of the role's level and the highest grant, so an Editor with a View grant still edits.
- Service accounts match no grant, because rows hold users and groups.
  A key sees a restricted folder only as an Admin or as its creator (`created_by_kind`, `created_by_id`).
- General is never restricted, renamed or deleted.
- Every person has one personal folder (`folders.personal`, `owner_id`), made by the `users_personal_folder` trigger and backfilled by its migration; `LevelFor` reads it first: the owner has Edit whatever their role and nobody else sees it, Admins included.
  It has no permission rows, nobody manages it, so it is never renamed, shared or deleted, and service accounts have none.
  Deleting a user deletes their personal folder and its dashboards, findings and saved searches (`users_personal_folder_contents` trigger and `ON DELETE CASCADE`), as it does their saved prompts.
- A dashboard or finding in a personal folder is private, and publishing it is a move out; `folders.MayMoveInto` is the one rule that a personal folder takes no moves for every move (`dashboards.Service.move`, `observations.Service.Move` and saved searches), and `ErrMoveIntoPersonal` maps to `409 personal_folder` with the wording of what moved.
  The web row menu hides personal folders as move targets as a display copy.
- `pickCreationFolder` is the one default folder for every create, agent commits and Save what was built included: requested, else the caller's personal folder, else General, else 403.
  A key's default is therefore General; nothing remembers where a caller created before.
- Folders sort by `(NOT personal, general, lower(title), id)` in `FolderFacts`, `ListFolderDetails`, `ListDashboardsByFolder` and `folderCursor`; change them together.
- A dashboard or folder the caller cannot see answers 404 `not_found` on every route, the same answer as an unknown id, so no route confirms that a hidden dashboard exists; a visible one with too low a level answers 403 `forbidden_role` with `forbidden.RoleMessage`.
  `ErrNoAccess` maps to that 404 in every handler, and `forbidden.AccessMessage` remains only for a principal whose id is not a user or key id (`ErrForbidden` on a feed).
- Every HTTP route keyed by a dashboard id declares `RequireDashboard`.
  List queries filter by `Levels.Visible()` and fail closed, services check writes themselves, and every count (lists, tag counts, `dashboard_count`) covers only folders the caller can see.
- An agent run is checked when it is enqueued and again when a worker claims it, after reloading the requester.
  The event stream re-reads the caller's access at every ping.
  Every claim names a `revisions.Claimant` and takes only rows of its assignee under the claim lock; admission (`Service.admit`) is the one place a claimed run is checked; outside runs no agent held for `revisions.UnclaimedFor` expire as `agent_unavailable` in `Service.sweep`, which the claim transaction and the `agent_requests_sweep` job both run.
- An activity row's folder follows its owner (`activity.Owner`, built by `OnDashboard`, `OnObservation`, `OnSavedSearch` or `General`; a finding's rows are owned by its dashboard when it has one and else by its observation, `finding.created` by its observation whenever `run_answer_kept_with_admins` holds for its run at append time, and `activity.finding_id` is still filled for them so the Down of migration 41 can find them): `InsertActivity` reads the owner's current folder, a global annotation takes General, and any other row has no folder and is visible only to its actor and to Admins.
  `Append` takes a shared advisory lock on the row's owner (dashboard, observation or saved search) and never locks the owner's row, because a delete holds that row and then cascades into child rows the appender may hold; a move of any of them updates the row, then runs `activity.Move` (the lock taken exclusively, then the rows rewritten), then appends the `*.moved` row, so a concurrent append either is moved with the owner or reads the new folder.
  A transaction writes or locks the owner's row before it appends, never after; a deleted owner's rows keep their folder.
  Activity reads filter by `Levels.Visible()` in SQL through `folders.AudienceOf`, the one definition of a reader's folders, Admin flag and identity, which search also reads, and the activity stream re-reads the principal with `RequestPrincipal` and its levels at every ping, as the dashboard stream does.
- Deleting a dashboard is permanent: foreign keys cascade its versions, threads, agent requests and import record.
  A `BEFORE DELETE` trigger on `dashboards` (`delete_dashboard_findings`) removes the chat-only answers of the dashboard and of its runs first (a saved answer keeps its place in the cascade, so `keep_copies_of_run` still sees its finding), because the cascade deleting a run fires `delete_unsaved_findings`, whose set-null on `agent_requests.applies_finding_id` would otherwise update a sibling run the same cascade is deleting (`tuple to be updated was already modified`, or a foreign key violation on a row the delete already touched).
  Inserts that lose the race against a delete map the foreign-key error (`db.IsForeignKeyViolation`) to 404.

## Database and dashboards

- `DB.WithSessionLock` is the session advisory lock on the direct connection; dashboard provisioning (`Provisioner.Run`) and `EnsureProvisioned` at boot run under it, so servers booting together create each provisioned dashboard and key once.
- Migrations are goose SQL files `internal/db/migrations/NNNNN_snake_case.sql`, numbered sequentially; never edit a merged migration.
- Migration 10 is a Go migration (`internal/db/specupgrade.go`, registered in `newMigrator`) with no file, so SQL numbering skips `00010`.
  A new SQL file takes the next number above both the highest file and every Go migration version, because a file reusing a Go migration's version stops the server at boot.
- Versions are immutable and linear (`parent_version = version - 1`).
  A save validates with `spec.Parse`, then runs every panel query through `internal/queryproxy` outside any transaction.
  `Save` with `Partial` (the `update_panels` save) runs only the changed panels and variables, as `ChangedSince` decides against the stored parent, never against what the caller claims, unless `needsFullCheck` says a `time` change or a title used by `$__dashboard` moved every result, and then it runs `checkSave`.
  An unchanged panel that started failing stays verified until a full save runs.
  The conditional `latest_version` update is the concurrency check (409 `version_conflict`).
  `Save` with `Merge` answers a stale save by merging it with `spec.Merge3` onto the latest version, checks the merged document with the save's own check and the latest as parent, and tries again on a lost race, three attempts in all; HTTP turns it on only for `"merge": "auto"`.
  A change sends one notification, inside its transaction, and `events.Notify` is the only sender on `events.Channel`: the live event's JSON with the appended activity row's `seq`, `{"seq":N}` when the change has no live event, or the live event alone when it appends nothing.
- A save that changes an existing panel's `w` or `h` sets `responsive: false` on it in `freezeResized` (`internal/dashboards/responsive.go`), called from `persist` before the replay check and from `commitRevision`; creates, imports, duplicates and restores never freeze, and the server never re-sizes a panel because of the flag.
- `agent_request_builds` holds one build per agent request: the canonical Spec, the carried `unverified` list, `planned_panels` and `panels`, so nothing parses the Spec to show progress.
  Every build write is fenced by the attempt (`status = 'running' AND attempts = @attempt`), so a worker that lost its lease writes nothing.
  Every build save with a parent is a partial check, as `ChangedSince` decides against the build, or against the base version for the first save of a revision, and placement moves change only `gridPos`, so they run no query.
  `CommitBuild` is one transaction that writes the version and deletes the build, and it runs no query because every build save was already checked.
  When `mustPropose` says the requester cannot edit now or the run acts in propose mode, and they can comment, `CommitBuild` instead proposes the build through the dashboards service's proposer (`Commit.Proposal`), in the proposal's transaction, which deletes the build fenced by the attempt and runs the changed panels' queries like any proposal save; the proposal belongs to the run (`proposals.run_id`), so a retried attempt folds into it, and a later `CommitBuild` of the request replays it.
  A run proposal counts as saved for settle, exhaust, cancel and the unclaimed sweep: the run succeeds with `result_kind = 'proposal'` and no `result_version` (`SucceedProposalRequest`), and its comment thread is not resolved.
  A create build passes through `closeLines` (`internal/dashboards/closelines.go`) in `commitBuild`, the one funnel of every commit path; revisions do not.
  A conflict at commit, or a session about to start on a build whose base is older than the latest version, first tries `RebaseBuild` (`internal/dashboards/build.go`).
  It rebases when `spec.Merge3(base, latest, build)` has no conflicts, then checks the changed panels with the partial check and moves the base with the attempt-fenced `RebaseAgentRequestBuild`, which leaves `saves` alone.
  After a commit conflict a clean rebase retries `CommitBuild` once in the same session.
  Otherwise the build is discarded, and the run restarts once from the latest version.
- A failed request keeps its build for `revisions.BuildRetentionDays`, and `claim` deletes the expired ones beside `FailExhaustedAgentRequests`.
  A lost lease or a shutdown release keeps the build, and the next holder re-seeds from it.
- `internal/revisions` cannot import `internal/dashboards`, so it takes the build through its `Builds` interface and `cmd/slashobserve-server/main.go` adapts the service with `buildStore`.
- `finish`, `planned_panels` and `row` exist only in the agent's tool schemas, through the `build` variant in `internal/agent/tools/wording.go`, and the agent's `update_panels` takes at most one item in `upsert`; a build save adds or changes at most one non-row panel (`onePanelPerSave`), and the server owns every position in a build: `x` and `y` from a panel body are never used, an unchanged panel keeps its stored `gridPos`, and a new, resized or re-rowed panel is placed by `place` (`internal/agent/tools/place.go`, first free spot of its row, a free `layout` spot first) through a panel patch, so `spec.ApplyPanelPatch` stays the only merge.
  A size field the model leaves out is chosen by `chooseSize` (`internal/agent/tools/sizes.go`, defaults by type plus the open line); a sent size is never changed.
  An MCP save that sends these fields is refused and keeps one version per accepted save.
  `import_grafana_dashboard` stays a direct first save and is refused in a run that already has a build.
- `CarryUnverified` (`internal/dashboards/unverified.go`) is the only rule for `dashboard_versions.unverified`; `CarryUnchanged` is its partial-check sibling, and `ChangedSince` reads the same `panelUnchanged` and `variableUnchanged`, which compare query text and datasource, the variables a panel reaches, and its `type`, `timeFrom`, `timeShift`, `maxDataPoints` and `interval`, so a title or `gridPos` edit is no change.
  Restore and duplicate copy the source version's list and run no query.
- `dashboard_versions.datasource_uids` is a generated column from the SQL function `observespec_datasource_uids(spec)`.
  Whenever the Spec moves datasources, change that function with `CREATE OR REPLACE` in a new migration that then runs `UPDATE dashboard_versions SET spec = spec`.
- Full-text search reads GIN expression indexes over `dashboard_search_vector(spec)`, `observation_search_vector`, `observation_block_search_vector`, `annotation_search_vector`, `message_search_vector` and `saved_search_search_vector` (`finding_search_vector` is still maintained but no query reads it, and goes with the `findings` table); a query uses an index only when it calls the same function on the same columns.
  Functions an index expression reaches either call only built-ins or declare `SET search_path FROM CURRENT`, because Postgres runs index maintenance and `pg_restore` with a `pg_catalog`-only search path.
  Changing one is a new migration with `CREATE OR REPLACE FUNCTION` and `REINDEX INDEX` of every index that reaches it; `observespec_search_text` and `observespec_search_code` follow the Spec shape like `observespec_datasource_uids`, and `message_search_text` follows the `@[Name](user:<id>)` mention syntax of `threads`.
  The five per-kind functions declare `COST 1000`, because the planner otherwise evaluates them on every version of every dashboard before joining to the latest one.
  `search_vector` joins its six parts (title and tags, body and query text, each in the `simple` and the `english` configuration) with a one-lexeme gap, because concatenated tsvectors continue each other's positions and a phrase would otherwise match the last word of one part followed by the first of the next.
- `SLASHOBSERVE_DATABASE_DIRECT_URL` is the session connection: `DB.Listen`, the migrator and its goose session lock use `db.DB.direct`, which is the main pool when the setting is empty; `Open` refuses a direct URL that reaches another database (`ErrDirectURLMismatch`, checked with an advisory lock before migrating). `NOTIFY` stays on the pooled transaction.

## Events, revisions and comments

- Event payloads carry ids and a capped author name, never comment text, so they stay below the 8000 byte `pg_notify` limit.
- `activity.Append` is the only writer of the `activity` table and runs inside the transaction of the change it records; the dashboard stream's frames never carry `seq`, because the broker strips it.
- Every activity read is `WHERE xid < pg_snapshot_xmin(pg_current_snapshot())` ordered and cursored by `(xid, seq)`, never by `seq` alone, with the horizon and the scan in one statement, because a transaction that took its xid first can append a lower `seq` after a later one committed; `seq` is only the public id of an event (`id:` in SSE and `Last-Event-ID`).
- An activity `data` object carries ids, numbers, enums, titles and the version summary, never prompt, comment, annotation or finding text, query text or Spec JSON.
- A run's cost is computed once, by `runsession` from the configured model and `llm/pricing`, and stored as `cost_usd` inside `run_usage`; there is no cost column, and runs from before it show none.
- `dashboard_versions.agent_request_id` stays unique: an agent request commits at most one version, so a retried run or a second commit returns the version it already created.
  The agent's `create_dashboard`, `update_dashboard` and `update_panels` change the build, never the history.
- A saved version always wins: before a failure is recorded, and when the lease sweep exhausts a request, the request counts as succeeded with the version saved under its id.
- A claimer holds its request by a `LeaseTTL` lease (60 s) that each `report_run` renews (`observe-agent` reports every 5 s while the run is in flight); a renewal that affects no row tells the claimer to stop and drops the attempt's work without finishing or releasing it.
  The renewal returns `cancel_requested_at`, and the first report that sees it answers `canceling` with `stop`, so a cancel takes effect within about one report plus the in-flight call.
- Cancel is a state move, not a registry or a notification: `POST /api/v1/observe/{id}/cancel` settles a queued run, or a running one whose lease expired, as `canceled` at once, and moves a running run with a live lease to `canceling` with `cancel_requested_at` set, which its worker finishes `canceled`, build kept; no worker claims a `canceling` run, and the claim-time sweep settles one without a live lease.
  `Service.finish` settles a canceled outcome as `canceled`, and the canceled outcome is recorded after the saved-version check (`endingOutcome`), so a version saved before the cancel took effect still makes the request `succeeded`.
- Only the requester may cancel or continue a request, not an editor and not an admin: `allowedActions` in `internal/revisions/machine.go` is the one rule, `requesterRow` answers anyone else 403 `forbidden` (404 for a new-dashboard request they cannot see), and `can_cancel` on `GET /observe/{id}` is computed from it.
  A dashboard runs one non-suggest request at a time, so a stuck revision holds back every other editor's revisions on it, and they queue behind it up to `MaxActive`.
  It ends only by its own limits, the requester's cancel, `SLASHOBSERVE_AGENT_RUN_TIMEOUT` when set, or the lease path after a crash; a graceful restart puts it back in the queue.
  Add no way for anyone else to stop a run.
- `ReadObserve` in `internal/revisions/service.go` is the one place that lets an Admin read an agent request it could not otherwise see; such a read is `read_only` with no actions, the list's `scope=all` (Admin only) uses the same rule for its actions, and write and build-save routes keep `GetObserve`, so they stay with the requester.
  An Admin also reads another person's build (`GET /observe/{id}/build` and its data routes) through `ReadObserve` and `dashboards.Service.ViewBuild`, which keeps the requester-or-Admin and dashboard-visible checks, so a build on a dashboard in someone's personal folder stays hidden from an Admin.
- A run's `state` changes only through `revisions.RunMachine` moves, and each queue query is fenced by `RunMachine.From(action)`; `docs/reference/states.md` is generated from the machine by `make generate`.
  Retry (`POST /api/v1/observe/{id}/retry`) is open to anyone who can see the run and may start that kind, and the new run is the caller's; the requester's own retry of a failed or canceled run sets `retries_id` on the new one, so it is retried once by its requester while anyone else's retry is a separate request of theirs and `runFacts.retried` drops `retry` and `continue` from its `allowed_actions`; a run has one successor, retry or continuation, held by the unique `agent_requests_successor_key` over `coalesce(retries_id, continues_id)`, so a concurrent Retry and Continue cannot both start.
- `runAllowed` is the one rule for who may start a run, keyed by the run's `intent` (`ask`, `apply` or `suggest`, the `agent_requests.intent` column; `source` is only a label derived from the row's shape by `RunShape.Source`): an `apply` run needs Comment on its dashboard, so a Commenter's run commits as a proposal, a `suggest` run needs Edit, an investigation that files into an observation needs the Editor role, and any other `ask` needs Comment on the dashboard or observation it is about, or the create rule when it is about nothing, so an ask on an observation by someone who may only comment stays a comment-level ask.
  A private ask (`intent = 'ask'`, a chat and no `observation_id`, with `dashboard_id` or `subject_observation_id` naming what it is about) writes nothing shared: it opens no observation, skips the investigation caps, its activity has no owner and its request and finding are read only by its requester and Admins; its tool writes are only the person-state writes (`writeScopeViolation`).
  A chat ask that is not an investigation (`AskedPrivately`, from the stored `investigation` column, not from `observation_id`) that someone else can reach through its observation is answered to anyone but its requester and Admins with `redacted: true`, an empty prompt, title, step messages and error text (`failure_code` stays), `read_only`, and no retry; once it is shared into a thread (`ShareRun`), a caller who can read that thread (`threadReads`) gets it in full, and a thread read that fails for any reason counts as unreadable.
  Thread runs never belong to a chat, so a chat ask's `thread_message_id` is set only by `threads.Service.ShareRun`, the requester's share of a finished answer into a thread on the ask's subject: the question and the run's reply are written in one transaction, the evidence passes the placement rule for the thread's folder, `run.share` is audited, and the finding is then read through that thread (`findings.WithThreads`), while the run itself stays the requester's.
  `RunFor` in `internal/agent/tools/runfor.go` maps the same intent to the agent's mode.
  `keep_build` needs Edit because it saves a version, so `runFacts.mayEdit` drops it from `allowedActions` for a requester who cannot edit; the `MaxActive` per-dashboard cap applies to Commenters as to anyone.
  `POST /dashboards/{id}/revisions` and a comment with `request_revision` check Comment, and `POST /dashboards/{id}/suggestions` still checks Edit.
- Continue (`POST /api/v1/observe/{id}/continue`) is a new request with `continues_id` set, and the stopped build moves to it with `MoveAgentRequestBuild` in the same transaction as the insert; the stopped request stays `failed`, so attempts only grow and every fenced write keeps working.
  The build row is the token that keeps Continue and save exclusive: `MoveAgentRequestBuild` needs `build_saved_at IS NULL`, `SaveStoppedBuild` returns `ErrBuildNotSavable` unless its delete removes exactly one build row, and the loser answers 409 `not_continuable` for Continue after a save, or 404 for a save after Continue because the build moved.
  A unique index on `continues_id` allows one continuation, and a revision whose dashboard has a newer version than the build's base answers 409 `version_conflict`.
- The continue note is optional, validated by `CheckContinueNote` (the `CleanPrompt` rule), stored only in `continue_note` on the continuation, and written into every seed of the continued run (continue, restart and conflict) after the seed sentence.
  The continue sentence (`brief.Continue`) is used only on attempt 1 of a continuation, through `brief.ResumeReason`; a later attempt seeds as a restart.
- `queue_position` is computed on read (1 plus the queued requests earlier in `(created_at, id)`, null unless queued), never stored.
- `ListAgentRequestBuildState` is the only reader of build progress, `continued_by` and `retried_by` for responses, one batch per page; the revisions list and the request list carry them for every row, and `buildState.progressFor` is the one place that nulls the build `title` for anyone but the requester.
- `SLASHOBSERVE_AGENT_RUN_TIMEOUT` defaults to no limit, and a set value is at least `1m`.
  `SLASHOBSERVE_LLM_REQUEST_TIMEOUT` accepts `0` for no limit too, and the run limit is config's decision, so `claims` has no default of its own.
  A run has no model-call cap, and without a run limit it ends at a commit, a failure, shutdown or lease loss.
  `SLASHOBSERVE_AGENT_RUN_MAX_COST_USD` (default none) is a spend limit, not a call cap: `runsession.overCostLimit` is checked on each usage report, so the report that crossed it ends the attempt, which fails `budget_exhausted` with its build kept; the server refuses to start with a limit and an unpriced model.
- `SLASHOBSERVE_AGENT_INVESTIGATION_CALLS` (6 to 60, unset by default) is config's decision and covers investigations and a create run (a Home chat message) until it saves its first panel: unset, config leaves it 0 and the defaults live only in `guard`, `InvestigationCallsFor(task)` per task type (`measure` 16, `logs` and `traces` 20, `incident` 30, `inventory` and `explain` 12, `DefaultInvestigationCalls` 30 for no type) and `DefaultChatCalls` 12 for the create run; `runsession.Service.watched` sets `guard.State.InvestigationCalls` from the setting or the task type when a session is created and the value is stored with the session, so a run keeps its limit across restarts and a changed setting applies to new runs only, and suggest keeps 12 and revise runs, and create runs once building, 6 as constants in `guard`.
- `SLASHOBSERVE_AGENT_INVESTIGATION_LOOP` (default on) is config's decision and registers `note_hypotheses` (`Deps.LedgerTool`, `agent/tools/ledger.go`, `OnlyIn` investigate, phase `ledger`) and makes `brief.Render` send `prompts.InvestigateWithLedger()` and the `<hypotheses>` block to a run whose `State.Loop` is true (set once in `Service.initial` for an investigate run with `Investigation`, so a plain ask gets neither); with it off the tool list, the prompt and the brief are what they were without the loop, which `ledger_test.go` in `agent/tools`, `agent/brief` and `runsession` pin.

  `triage.Leads` turns the sweep's first `triage.MaxLeads` candidates into leads stored in `State.Triage.Leads`, and `State.seedLedger` (`runsession/candidates.go`) starts an empty ledger of a loop run whose task `worksCandidates` (incident or no type) with one open hypothesis per lead, keyed by the candidate id, when the sweep is stored and when a new attempt copies it.

  The stage is derived from the ledger and the call count, never declared by the model.
  `windowLimit` reads `Loop.Limit`, and `State.noteLedger` feeds `guard.State.NoteLedger`, which grows the limit by `LimitGrowth` on progress backed by a read, times the number of seeded candidates (`Loop.Candidates`) the ledger closes with a closing and evidence.

  `revisions.Usage.CallLimit` and `StageAtSave` record the end state.
  With it off `Loop` is nil and every guard path is the one it was.
- `SLASHOBSERVE_AGENT_FINDING_GROUNDING` (`off`, `report` or `enforce`, default `enforce`, in `grounding.ParseMode`) is config's decision and gives every run that can save a finding (investigate, create and revise, never suggest) a `grounding.Record` (`agent/grounding`) in `runsession.State.Grounding`, set once in `Service.watched` for every assignee, so a stored session keeps its mode; with `off` the record is nil, nothing is recorded or checked, no read carries facts and every prompt is the one without them.
  Facts: `State.issueFacts` passes each successful result of a tool in `grounding.factSources` (`measure_window`, `measure_aggregate`, `trace_stats`, `trace_error_origins`, `trace_slow_path`, `get_trace`, `log_facets`, `log_patterns`, and the `min`, `max` and `last` of `query_range` and `query_instant`) through `Record.IssueFacts`, which adds a `facts` map of value key to id (`f1`, `f2`, unique per run, the same value read again keeps its id) and keeps each fact with its full-precision value, kind, unit, labels, window and query; the record holds the newest `grounding.MaxFacts` (400), at most 120 per read, plus every trace and span id a result showed, never logged and never returned by the API.
  Reads: `State.noteGrounding` feeds the record only from successful datasource reads (`groundsFindings`: `guard.ReadsData`, the query tools and the `dataReads` table, or a result with datasource discovery), never from tools that return SlashObserve's own stored text such as observations, chats or comments, so a new datasource read tool joins `dataReads`; it takes the names of its discovery and the ranges `tools.NotingRanges` collected from `resolveRunRange`, and keeps at most `grounding.MaxValues` numbers at 3 significant figures, grouped per read because derived figures pair values of one read, the times results showed, names only from label values, name fields, a trace's services and discovery (kept apart and never evicted), and never a number under a time key or an object key.
  A `call_mcp_tool` result is the one exception to that reading: `Record.AddSourced` (`agent/grounding/sourced.go`) takes only names from its `text` (ASCII identifiers of 3 to 64 bytes, at most 500 per result, the newest 2000 kept in `Record.Sourced`, apart from the other names), never a number, time, trace id or fact, because the server cannot vouch for what an outside tool computed; the name checks and the cause scoring read them like any other name.
  In `factSources`, a `log_facets` count of a field without `exact: true` and a `log_patterns` count with `source: server` are `Fact.Sampled`, which `Format` always renders after `at least` and never rounds up, and `Fact.Signal` is set to logs for a `measure_aggregate` result with `store: loki`, so `signalOf` classes it as logs like the `log_` tools.
  The check: `State.checkGrounding` runs `Record.Review` on `save_finding` before the guard admits it: placeholders `{{fN}}` with their unit, percent and significant-figure options (`Ledger.Render`, an option may not move the value more than 1%), the `answers` list (`Ledger.AnswerProblems`: a fact the run does not hold, two facts more than 1% apart or two trace ids for one quantity, an answer the Markdown never states), two cited facts of one quantity (`conflicts`), every typed figure (`figureProblems`: within 1% of a fact and its written precision, else within 2% or the written precision but never 10% of a value read or derived from one read, with question numbers, versions, ports, statuses, windows, years and small unitless numbers left out), trace and span ids (`traceIDProblems`: whole and read), `root_cause.component` (a name seen) and `onset` (inside a queried range or next to a time a result showed).
  The items reach the tool through `tools.WithUnverified` and are stored in `findings.unverified`, and the ledger through `tools.WithFacts`, so `save_finding` renders every placeholder into the stored text (an unknown fact as `grounding.UnreadMarker`) and nobody downstream sees one.
  `runsession` adds one item only to the send-back, never to the stored ones: a `measure`, `logs` or `traces` run (`answersAFigure` on `State.Task`) whose finding states a figure but lists no `answers` (`grounding.MissingAnswers`).
  The prompts: with a record, `brief.Render` sends the facts variant of the investigate text (`prompts.Variant.Facts`: the core without `enforcedRules`, plus `facts.md`) and adds `factsNote` to the context of a create or revise run.
  With `report` the items are stored and nothing else changes; with `enforce`, `guard.State.Grounding` sends the first save with any item back once through `unbackedFinding`, which neither counts a rejection nor ends the run, and marks the turn rejected so the next call may read past the limit; the second save is admitted whatever it holds, with its items stored.
- `SLASHOBSERVE_AGENT_INVESTIGATION_BRIEF` (`on` or `off`, default `on`) is config's decision and makes `main.go` give `runsession` a `triage.Service` through `SweepWith`.
  `runsession.Service.preflightOnFirstBrief` sweeps only on a `Fresh` brief of an investigate run with `Investigation`, outside the session lock and slot, stores `State.Triage` (block, reads, duration) once, copies it from the prior attempt's session in `create`, and records one step; `brief.Task.Triage` adds the block to the investigation context, so a compaction, resume or restart never sweeps again.
  `agent/triage` reads only through the tool registry (`ToolReader`, and `Registry.SweepRange` for whole range frames) over `VisibleToEveryone` sources without the audit datasource, within `triage.DefaultLimits` (40 reads, 20 s, 4 at once), and its rules are pure functions there (`Onset`, `Cluster`, `Render` under `MaxBlockBytes`); the block is never logged.
- `SLASHOBSERVE_AGENT_WORKERS` (default 8, 1 to 64) is config's decision; the pool floor is `max(16, 2*workers+8)` (`poolFloor` in `main.go` gives `2*workers+8`, `minPoolConns` in `internal/db/db.go` the 16) unless the URL sets `pool_max_conns`.
  The progress guards steer first and stop after: 3 rejected saves in a row (an accepted save resets the count), where a `save_finding` over the word limit (`tools.CodeFindingTooLong`) is counted apart in `State.LengthRejections` (5 in a row, `MaxLengthRejections`), each kind zeroes the other's run, and `State.RejectedSaves` caps rejections of any kind at 8 (`MaxRejectedSaves`) until a save is accepted, so alternating kinds stay bounded, with `guard.Stop.Message` carrying the stop text when the generic "3 saves in a row" would be wrong; reads refused from the sixth model call of a save window (12 in suggest mode, `SLASHOBSERVE_AGENT_INVESTIGATION_CALLS` in an investigation and in a create run before its first build save, decided only by `State.windowLimit`), except beside a save and in the call after a rejected save, with a nudge one call before; `no_progress` after two turns in a row in which every call was refused, where a turn whose `note_hypotheses` call changed the ledger or was sent back for a fix is not counted for up to `maxLedgerTurns` (4) in a row; a repeated save and a third identical read are refused; errors and `query_range` or `query_instant` results are never replayed; and the churn rule, `maxChangesPerPanel` 4 and `maxChurnedSavesInRow` 3, which measures progress by content (`Result.Edits`, from `editsOf` in `agent/tools/build.go`: any panel JSON, variable or dashboard-level field that differs from the build before, so a description-only save is progress) and not by `ChangedSince`, which only decides re-verification.
  A save that deletes a panel does not count the panels it adds as progress (`Edits.Added` and `Edits.Deleted`; they still count toward the per-panel changes), so one replacement passes within the 3 tolerated saves and repeated delete-and-add swaps end in `no_progress`.
  A session is compacted, not renewed: after an accepted save past `SLASHOBSERVE_AGENT_SESSION_RENEW_KIB`, on the first cut-off (`max_tokens` or `call_timeout`), once per run when the model answers without a tool call while planned panels are missing, and once per create or revision run when it answers without a tool call before any build exists (`Compact` then drops that answer so the session continues), `llm.Session.Compact` keeps the last 4 turns within 32 KiB (results cut to 2 KiB, thinking kept only on the last assistant turn) behind a new first message with the build, the seed sentence and the discovery digest (`internal/agent/brief/digest.go`, 4 KiB, never logged).
  The renewal size is `SLASHOBSERVE_AGENT_SESSION_RENEW_KIB` (default 256, 32 to 4096), and its default lives only in `defaultSessionRenewBytes`.
  A second cut-off with no accepted save in between ends the run with its code.
  A provider session starts only at the start of an attempt and after a conflict restart, never as a recovery.
  Request-side pruning replaces old read results with stubs in what is sent once older prunable results reach 64 KiB and keeps the last 4 assistant turns whole; the stored history keeps everything.
  `dashboards.ErrBuildLost` is a lease loss: the run session drops the attempt's work and writes nothing more.
- A shutdown release keeps the steps, so the re-claim continues the same step list (the most recent `MaxSteps`, 1000, per attempt).
- A stopped build is saved through `POST /api/v1/observe/{id}/build/save`, only by the requester.
  The request stays `failed` with its failure code, and the same transaction sets `build_saved_at`, `result_version` and `dashboard_id`, so `succeeded` always means the agent finished.
  A newer version on a revision answers 409 `version_conflict` and keeps the build; nothing rebases it.
- `SLASHOBSERVE_LLM_EFFORT` is validated per provider in config and reaches an OpenAI-compatible provider only when set; `llm.Tuning.ForCall` raises it one step for the planning call and halves `max_tokens` (floor 8192) for the others.
  `config.LLM.QuestionEffort` is the effort of a run that `revisions.Request.Investigates` (an `ask` that is not a new-dashboard run, the runs `RunFor` maps to investigate): the set value, else `high` on Anthropic only (`defaultQuestionEffort`), else nothing; `claims` puts it in the built-in claimer's offer through `Config.Model(question)`, so observe-agent needs no change and every other run keeps the provider default.
  `SLASHOBSERVE_LLM_IDLE_TIMEOUT` (default 180 s, `0` off) is the idle watch of every streamed call, and `SLASHOBSERVE_LLM_REQUEST_TIMEOUT` covers `llm.Retry`'s attempts.
- A request from a comment resolves the open thread in the same transaction, unless a message that mentioned an agent started it (`thread_message_id`): that run posts its reply instead and leaves the thread as it is.
  `Service.recordEnded` is the one place a terminal move (`finish`, the release settle, every group of `sweep`, `Cancel`) records its activity and calls `Threads.RunEnded`, so the sidecar's `runsession` and a connected agent's `finish_run` (which both end through `finish`) answer the same way.
  The call runs in a savepoint and is logged as `agent_request_thread_end_failed`, so the request still records its end.
  The reply is not best effort: every `sweep` calls `RunEnded` again for a run with `thread_message_id` that ended within `ReplyRetryFor` (24 h) and has no `agent_requests.thread_replied_at` (`ListRunsAwaitingReply`, newest first, `ReplyRetryBatch` per sweep), so a failed or lock-skipped reply is posted by a later sweep, and `InsertRunReply` keeps it to one; `MarkRunReplied` sets the column in the reply's transaction, so a reply a person deleted is never posted again.
  Retry and Continue copy `thread_message_id` and `thread_context` (only while the message exists; a dashboard chat's `prompt` run has no message, so Retry recomputes its transcript and Continue keeps the one the stopped run had) and the assignee to the new run, and refuse with 409 `assignee_unavailable` when the grant is revoked, expired or not the caller's or the service account no longer takes runs (the `MentionableGrant` and `MentionableServiceAccount` queries, `checkAssignee`), never giving the run to the built-in agent; only a built-in run needs the model provider, and `revisions.Request.ThreadContext` reaches the model through `brief.Render` and a connected agent through `claim_run`'s `thread_context`.
- Without an LLM provider, comments do not enqueue, so turning an agent on later never replays old comments.
- An observe request has no dashboard until it finishes.
  `dashboard_id` is filled from the version saved under the request id, so queue lookups of a saved version use the request id only.

## Query proxy and datasources

- An HTTP datasource (Prometheus, Loki, Tempo, Elasticsearch) builds its client on `datasource.NewHTTPTransport`, never a bare clone of `http.DefaultTransport`: that keeps 2 idle connections per host, so a burst of concurrent calls redials and the closed sockets exhaust the ephemeral ports within a minute (`datasource_unavailable: connection failed`).
- The proxy accepts no query text (403 `query_not_in_spec`).
  The one exception is `POST /api/v1/datasources/{uid}/preview`, which places a draft panel from a signed-in user with Comment on the dashboard into a saved version with `spec.WithPanel`, runs it with `DraftLimits` (which apply to every query whose text did not come from a saved Spec), never caches or coalesces it and refuses a bearer key (403 `user_session_required`).
  Its observation sibling `POST /api/v1/observations/{id}/blocks/preview` (`proxyhttp/observation.go`) wraps a draft panel the way a panel block is wrapped (`observations.Service.DraftPanelData`, for a caller who may add a block, keeping an edited block's variables and range), reads under the observation's folder (`readingStored`) and runs the same way.
- The proxy's caches are shared by everyone, so a version whose queries reference `${__user.*}` is cached per principal.
  The runner that validates saves stays uncached.
- The second exception is `GET /api/v1/observe/{id}/build/panels/{panel_id}/data` and `.../build/variables/{name}/values`: they load the requester's stored build on the server, which an Admin may read too (`proxyhttp/build.go`, through `dashboards.Service.ViewBuild`), run under `DraftLimits`, never cache or coalesce, and refuse a bearer key (403 `user_session_required`).
- The third exception is `POST /api/v1/datasources/{uid}/query` (`proxyhttp/explore.go`), the logs page's, trace view's and CLI's explore query: it runs the given text against one datasource as a one-query panel with no variables under `DraftLimits` (`limit` only lowers `MaxRows`), never caches, coalesces or aligns an instant range, counts against the in-flight cap and accepts service-account keys from Viewer up.
- `GET /api/v1/datasources/{uid}/traces/{trace_id}` and `POST /api/v1/datasources/{uid}/trace-stats` (`proxyhttp/trace.go`, `proxyhttp/tracestats.go`) are the explore query's siblings: a whole trace under `datasource.TraceSpanBudget` (20,000 spans, the earliest kept, `meta.rows_total` and `meta.truncated` say the cut) and span counts, quantiles and a duration histogram over a TraceQL filter or a SQL condition, both through `datasource.TraceSource` and `datasource.TraceStatsSource`, under `DraftLimits`, never cached, one upstream slot per request, from Viewer up.
- The fourth exception is `GET /api/v1/findings/{id}/panels/{panel_id}/data` (`proxyhttp/finding.go`): it runs only a query stored with a finding and checked when the finding was saved, under the access of the finding's observation (its requester or an Admin while it is a chat-only answer) and `DraftLimits`, never caches, and refuses a bearer key (403 `user_session_required`).
- The fifth exception is `GET /api/v1/public/{token}/panels/{panel_id}/data` and `.../variables/{name}/values` (`proxyhttp/public.go`): no session, the link's dashboard at its latest version only, the shared caches, and in-flight slots keyed `public:<link id>`.
  A frozen link uses its stored selections and a free one accepts a value only when `public.EffectiveSelections` finds it among the options the values path computes (through `variableOptions` and the values cache); a version that reads `${__user.*}` answers 404.
  `GET /api/v1/public/{token}` serves the Spec with every panel and variable `query` emptied and the dashboard's `tags` and `links` dropped.
- The sixth exception is `POST /api/v1/datasources/{uid}/trace-logs` (`proxyhttp/tracelogs.go`), the trace view's and the `logs_for_trace` tool's path to the lines of a trace or span: `datasource.TraceLogSource` (Loki and ClickHouse) builds the query itself from the hex-checked ids, so no query text crosses the API, and it runs under `DraftLimits` with the explore slots and error codes.
- The seventh exception is the ad hoc chart of the `show_panel` tool, which has no route: `proxyhttp.PanelData` runs the given text against one datasource as a one-query panel with `Explore` and `DraftLimits`, never caches, and caps the encoded data at `MaxAppDataBytes` (2 MiB, `limit_exceeded` above it); a saved panel of `show_panel` runs its stored query through the same function with the range from `ResolvePanelWindow`, the dashboard route's own resolution.
- `POST /api/v1/datasources/{uid}/log-facets` (`proxyhttp/facets.go`) and the `log_facets` tool count the top values of a logs query's fields through `datasource.LogFacetSource` (Loki and ClickHouse), a direct datasource call under `DraftLimits` and one upstream slot, in which the adapter fans out at most 4 calls at a time; Loki index labels count bytes from the index volume API and say `unit: bytes`, every other field says whether it is exact or sampled.
- `POST /api/v1/datasources/{uid}/log-context` (`proxyhttp/context.go`) and the `log_context` tool read the lines just before and just after one line through `datasource.LineSource` (Loki and ClickHouse), anchored on the line's `TimeNs`, as two `Lines` calls at once under `DraftLimits`, each with one upstream slot; the endpoint counts against the explore slots.
  `GET /api/v1/datasources/{uid}/tail` (`tailhttp`) polls the same `Lines` forward from the newest `TimeNs` plus one nanosecond, capped at the poll's start, and every `datasource.LagSource` (Loki, ClickHouse, Elasticsearch, OpenSearch; `datasource.DefaultTailLag`) reads that many seconds before the cursor again and drops rows already sent by id, or by labels and every field of the row, so a line is sent once and a late one still arrives.
- `POST /api/v1/datasources/{uid}/log-patterns` (`proxyhttp/patterns.go`) and the `log_patterns` tool share `Runner.LogPatterns`: a `datasource.LogPatternSource` (Loki, its pattern API, a bare stream selector only) answers `source: loki`, and `ErrNotFound` from it, or no such source (ClickHouse), reads the newest `sample` lines through `LineSource` and clusters them with `logpatterns` as `source: server`; one upstream slot per call, under `DraftLimits`.
- `spec/examples/time/resolve-cases.json` keeps the Go and TS relative time resolution in step.
- Variable values reach queries only through `internal/datasource/macros`.
- A Spec names a datasource by uid or as `${name}` naming a datasource variable.
  `spec.DatasourceVariableName` is the only parser.
  A literal uid's type comes from the registry and a `${name}` reference's from the variable's `datasourceType`, so the query proxy, not `spec.Parse`, rejects a macro the type lacks (`unknown_macro`).
- `GET /api/v1/datasources` never returns a URL, address, user or secret.
  Only the Admin-only `GET /api/v1/datasources/{uid}/config` returns the address and login, and no route returns a stored credential; app datasources are sealed with `sealed.Key` and managed through `datasourceadmin`, HTTP and CLI only.
  The health `message` is a fixed string chosen by error kind, never the error's own text.
  Datasources never gate `/readyz`.
  A datasource's health probe is a cheap read that proves it can answer queries (Loki asks `vector(1)+vector(1)`, never `/ready`, which fails while an ingester joins the ring or under load).
  `Registry.Health` serves a cached failure at once and refreshes it in the background once it is 2 seconds old (`Recheck` probes inline after 2 seconds), and a healthy status lasts 10 seconds.
  `Registry.Answered` turns a cached transient failure (`ErrUnavailable`, `ErrTimeout`, `ErrLimitExceeded`) into healthy and never a configuration failure such as `ErrIsOpenSearch` or `ErrNoIndex`; only the runner's `upstream` (panel and variable queries) and `RunPage` (the explore page read) call it, not the trace, facets, patterns, services, tail or log context reads.
- ClickHouse is queried only as a `readonly = 2` user with `SELECT` on the OTel database, and the server refuses a user that is not read-only.
  The compose user `slashobserve_ro` is created on first boot by the distroless image's `docker-init` from `internal/datasource/clickhouse/testdata/readonly_user.sql`, mounted into `/docker-entrypoint-initdb.d`: the same definition, with the same fixed development password, the integration tests use.
- Any feature that fetches a URL taken from user content goes through `egress.Client`, never its own `http.Client`.
- A webhook request goes through `egress.Client.Send`; its URL, headers, body and the receiver's response are never logged or stored, only the status, an error code and the duration.
- A rule that lives only in a schema description belongs in the authoring guide, because the model reads `prompts.Schema()`, which strips the annotations.

## Logging

- `log/slog`; request logs record the path, never the query string.
- The server never logs secrets, prompt text, query text, variable values, tool results or MCP client names.
  OAuth codes, tokens, `state`, redirect URIs and registered client names are never logged either.
  The `asset fetch failed` and `action run` lines never hold URLs, paths, queries, bodies or action inputs.
- The one exception to the provider-message rule is `SLASHOBSERVE_LLM_LOG_PROVIDER_ERRORS`: when on, `llm.CallError.ProviderMessage` (scrubbed of the key and control characters, capped at 1024 bytes, never in `Error()`) is logged as `provider_error_message` on a failed `llm call finished` line.
- A failure is a fixed message plus `logattrs.Failure(code, err, ids...)` and the relevant ids, never `err.Error()`, and a panic is logged by its type only.
- `sloglint` forbids the literal attribute keys `error` and `err` under `internal/`, `cmd/` and `pkg/`.
  It cannot see a key built through a variable or helper, or `err.Error()` under another key, so review those by hand.
- A fatal startup error keeps its text only through `described` in `cmd/slashobserve-server/main.go`, for messages the server wrote from settings; never echo a URL setting.
- Handlers pass an error through `clientgone.Handle` before logging at ERROR or answering 500, because a caller that went away mid-request is not a server failure (a cancellation on a live request context still is).

## API contract

- Every `/api/v1` route is documented in `api/`.
  Only the e2e stack runs with `SLASHOBSERVE_API_CONTRACT_CHECK=true`, which turns a request or response that breaks the document into a 500 `contract_violation` and makes `scripts/e2e.sh` fail; it never belongs in production.
- A query parameter a route does not document is reported in `X-Unknown-Query-Parameters` and fails the contract check; a list route (a `GET` whose `operationId` starts with `list`) answers 400 `invalid_request` for an unknown parameter, a value its schema refuses or a malformed query string (`internal/server/queryparams.go`, the one place); add a new parameter to the route's YAML or clients will be refused.
- `/api/v1` answers `Cache-Control: no-store`; a safe, large read opts out through `httpapi.RevalidatedJSON` (private `ETag`, `Vary: Authorization, Cookie`, 304), and never for query proxy data.
- Document every status a handler can return, and keep `additionalProperties: false` on response objects so new fields must be documented.
- Wire conventions: JSON field names are `snake_case` (the Spec document inside a response keeps its camelCase), times are RFC 3339 UTC strings, errors are `{"error","code"}` plus optional named fields, 401s carry `WWW-Authenticate: Bearer`, and lists use opaque `cursor` and `next_cursor` (null at the end) with `limit`.
